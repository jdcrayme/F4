# Real-Airbase DIGI Scenario via the Shared f4-Renderer Layout Pipeline

## Answer to the design question
Agreed on the direction. Concretely: relocate the world-viewer's proven, Raylib-free airfield-geometry builder into f4-renderer (plus its generic draw primitives), reference a real world JSON from the scenario (`airbase_source`) instead of baking or hand-authoring geometry, fix `derive_airfield_from_objective` — which is provably wrong on real PHD data — and wire the user's real Falcon install into CMake as the data source. This is the first concrete increment of the long-term "f4-renderer renders the world from a bubble" vision; terrain/culling/LOD are follow-ups, not scope.

Decoded real-data facts this plan relies on (from korea_real.world.json analysis):
- Runway lists mix point kinds in fixed order: [PT_RUNWAY far-end marker, PT_TAKEOFF, PT_TAKE_RUNWAY, then an ordered taxi polyline (runway→ramp direction, ~150-220 ft spacing)]. Taxi is a polyline, not a graph — reverse it for ramp→runway; no path-finding needed.
- Runway dims come from PLT_RUNWAY_DIM quads (e.g. 8438×176 ft); dim-list heading_deg is garbage (236°) — use the quad geometry.
- Point x/y are already ENU feet relative to the objective center (grid×1024) — no rotation needed.
- This Steam PD has NO parking spots anywhere; all 42 airbases share one identical template (runways 02/20). Parking is synthesized at the ramp end of the real taxi polyline (offset perpendicular, 80 ft spacing) — derived from real geometry, not invented.

## Step 1 — Move the layout geometry builder into f4-renderer
- Move `f4-world-viewer/src/ground_layout_models.{hpp,cpp}` → `f4-renderer/include/f4/renderer/ground_layout_models.hpp` + `f4-renderer/src/ground_layout_models.cpp`; namespace `f4::viewer` → `f4::renderer`; API unchanged (`build_airfield_geometry_3d`, `AirfieldGeometry3D`, `LayoutQuad/Line/Marker`, type predicates). Deps (f4-entities types, f4-math Vec2) already link PUBLIC in f4-renderer — no CMake dep changes.
- Move `test_ground_layout_models.cpp` → `f4-renderer/tests/` (drop the `../src` include hack; link f4-renderer + IMGUI_SOURCES per the existing pattern). 18 tests keep passing.
- New `f4-renderer/include/f4/renderer/layout_draw.{hpp,cpp}`: the generic primitives currently inside world-viewer's ground_layout_3d.cpp (draw_ground_quad / draw_layout_line / draw_layout_marker / draw_ground_grid + world-to-screen label helper), taking an ENU origin offset so callers render objective-local geometry anywhere in the world.
- World-viewer consumes `f4::renderer::` versions; local copies deleted; viewer tests stay green.

## Step 2 — Fix airfield derivation for real PHD data (campaign_bridge)
Rewrite `derive_airfield_from_objective()`:
- Group PLT_RUNWAY lists by runway_num; select the active direction by heading (closest to requested `active_heading_deg`, default first list).
- threshold = PT_TAKEOFF point + ~305 ft along heading (or reciprocal list's PT_RUNWAY marker when present); runway_end = own PT_RUNWAY marker; heading = list heading_deg.
- Parse PLT_RUNWAY_DIM quad → `runway_length_ft` / `runway_width_ft` (new ScenarioAirfield fields; replaces the hardcoded 100 ft runway width in the player).
- taxi_route (ramp→runway) = reversed taxi polyline + PT_TAKE_RUNWAY + PT_TAKEOFF (hold-short at the takeoff point); taxi_in_route = forward order (takeoff → take-runway → polyline → ramp).
- Parking spots synthesized at the polyline terminus, perpendicular offsets, facing along the final segment; returned for spawn use.
- Keep the current heuristic as a fallback branch for degenerate/unknown layouts (existing tests unchanged).
- New unit tests feeding a real-template GroundLayoutList (numbers from the analyzed Kunsan-class objective) asserting threshold/end/heading/dims/routes/parking positions.
- TakeoffModule/LandingModule taxi capture radius (50/40 ft today) raised to fit real polyline spacing (~150-220 ft) — exposed config, set from the derived route.

## Step 3 — `airbase_source` in the scenario schema
- Optional scenario block: `"airbase_source": { "world_json": "<path>", "objective": { "name" | "grid_x","grid_y" }, "active_heading_deg": 20 }`.
- load_scenario resolves world_json against the scenario dir; Simulation::initialize (when present): `WorldState::load` → find objective → Step-2 derivation overrides `scenario_.airfield`; scenario aircraft with `"parking": "auto"` get the synthesized real parking spot + heading.
- Scenario gains `layout_lists` (vector<GroundLayoutList>) + `layout_center` (ENU WorldPosition) so the renderer can draw the real layout without touching f4-world.
- Loader tests: selection by grid coords/name, missing objective throws, hand-authored airfield block still works when airbase_source is absent.

## Step 4 — Player renders the real layout through the shared builder
- airport_geometry: when the scenario carries layout_lists, build via `f4::renderer::build_airfield_geometry_3d` and draw through the shared layout_draw primitives translated by layout_center; keep the synthetic path for hand-authored scenarios (existing tests).
- Real dims drive the runway surface width; flight-plan/approach/taxi overlays unchanged (already scenario-ENU).
- `digi_full_mission.json.in`: switches to airbase_source; waypoints authored in an optional runway-relative frame (`"frame": "runway"` → loader rotates about layout_center by runway heading) so one template works for any runway/airbase; the fake `airfield_features` list is dropped (real FeatureEntryState models are a follow-up).

## Step 5 — CMake real-install wiring
- Cache var `F4_INSTALL` (e.g. -DF4_INSTALL="D:/SteamLibrary/steamapps/common/Falcon 4.0"). When set: custom target regenerates `Build/korea_real.world.json` via cam2json (install save1.cam + install terrdata/objects). When unset: fall back to the bundled fixture theater DB (highway-strip template, same list structure) so the derivation path is always exercised; the full-mission test skips if the file is absent (existing pattern).
- digi_full_mission.json.in references the generated file; target dependencies enforce generation order.

## Risks
- One shared template for all 42 airbases in this PD — real data, but per-base uniqueness comes with other theater DBs later; the derivation is per-objective so it generalizes.
- Mission-control tuning may need small adjustments for the real runway (heading 02, 8438 ft) — tolerances verified in Step 6.
- The ImGui-source linkage quirk in f4-renderer tests is a known, already-solved pattern.
